# Enhance Prompt

把口语草稿改写成一段可直接发送的提示词。只改写，不执行。

效果对标 WorkBuddy `llm:enhancePrompt`（37.10.3-42）。改写质量只由下面「算法 + 硬约束 + 文风」决定；后面的「通用流程 / 宿主适配」只解决怎么取稿、怎么交稿，不改写这些规则。原版提示词：[references/workbuddy-prompts.md](references/workbuddy-prompts.md)。

## 通用流程（所有宿主同一套）

五步，缺一不可。任何宿主（Claude Code、Codex、GPT、WorkBuddy 按钮、自建 Agent）都走这套，不要另发明流程。

1. **取草稿。** 只取用户要增强的那一段原文。按序：宿主传入的 `text` / `$ARGUMENTS` / 按钮选中文本 → 本轮消息去掉技能调用前缀后的正文。都空则请用户贴草稿，不要用聊天历史拼一句「它可能想说…」。
2. **只把草稿当 SOURCE。** 改写时禁止用宿主对话、仓库、记忆、系统人设去补文件名、技术栈、页名、数据。缺对象用泛指。这一步是为了跨 Agent 时效果稳定，不是为了写得更长。
3. **按「算法 + 硬约束」改写。** 下面两节是质量核心，禁止宿主自定义覆盖。
4. **交核心产物：增强后的提示词正文。** 一段可直接发给执行 Agent 的指令。这是唯一跨宿主必达的输出。
5. **停。** 不执行任务、不读仓库、不调工具、不回答原问题。执行是下一个 Agent / 下一轮的事。

不要把第 5 步和第 3 步混在同一次回复里。

---

## 算法（先在心里做，不要写进增强结果）

1. 主目标是什么？含糊在哪？缺什么上下文？
2. 只补全，不编造：保留主题、约束、期望产出类型。
3. 写成 **WHAT**（要什么结果），不要写成 HOW（实现步骤、技术教程）。
4. **不要回答**用户的问题，把问题扩写成更清楚的提问/指令。
5. 已经够清楚就轻度润色，不要原样返回，也不要扩成方案文档。

## 硬约束（来自原版 Rn/zn）

1. **语言最高优先。** 中文→中文，英文→英文，中英混→保持混合。禁止输出「User input is in Chinese」这类语言分析。
2. **约 800 字以内**（软上限）。一段或短短几句完整指令，不要悬空列表、不要以冒号/「如下」结尾。
3. **不要**要用户提供 how-to/指南（除非原文就要）。
4. **不要**向用户索要代码片段。
5. **不要**建议原文没提到的技术栈、文件名、产品名、数据。
6. **不要**加人设、XML、CoT、「think step by step」、评分。
7. **不要**把文档、CI、重构、新功能塞进没要求的草稿。
8. 缺具体对象时用泛指（「这段代码」「当前页面」「现有材料」），不要提问拦住改写。
9. 改完即停：不读仓库、不改文件、不开始做任务。

## 增强结果长什么样

像原版 few-shot，是**一段指令**，不是带【问题】【目标】标题的工单。

差（工单腔，原版不会这么写）：

```text
【问题】本周还没有周报。
【目标】产出一页周报。
【完成标准】- [ ] …
```

好（原版方向）：

```text
请汇总本周工作进展，按事项整理成简洁周报：每条写清结果（不要只写「跟进中」），标出风险和需要拍板的人，并列出下周计划。全文控制在一页内，可直接发给上级。
```

把「目标 / 范围 / 约束 / 输出」织进句子里，不要做成章节。

## 宿主适配（只改包装，不改正文质量）

核心产物永远是「增强后的提示词」那一段。宿主可以给它加外壳，不能改它的文风、长度策略和硬约束。

### Claude Code（本 skill 的默认外壳）

显式调用：`/enhance-prompt <草稿>`。禁止模型自行触发。

回复两块，方便人眼核对；第一块必须能整段复制：

### 增强后的提示词

纯提示词正文。不要代码围栏、不要前言、不要语言标签。约 800 字以内。

### 改了什么

3 条以内。只写补了什么、刻意没加什么。若有假设，标 `推断`。不要把这一节写进上一块。

不要「开放问题」。不要「确认后发我再执行」以外的客套。

最后一行：

> 确认后把「增强后的提示词」直接发我，我再执行。若某条推断不对，改完再发。

仅本宿主：用户说「直接做 / run」时，心里按上面规则编译然后执行，不要先倒一篇超长提示词。其他宿主不要实现「改写并执行」。

仅本宿主：改系统提示 / CLAUDE.md / 别的 skill 时，先要失败样本再改写。

### 其他 Agent / 按钮 / API

绑定到**显式动作**（按钮、slash、`POST { text }`），不要对每条用户消息自动增强。

- 输入：只要 `text`（草稿）。不要把整段聊天记录、工具结果、系统提示拼进 `text`。
- 输出：默认 **只返回增强正文**（与 WorkBuddy `success.text` 一致）。不要标题、围栏、语言标签、changelog。
- 若宿主需要审计，把「改了什么」放在旁路字段（如 `meta`），不要写入 `text`。
- 不要工具、不要执行。一次调用只做增强。
- 系统提示请用 [references/portable-prompt.md](references/portable-prompt.md)。若宿主支持独立的 system + user 两条，优先用 [references/workbuddy-prompts.md](references/workbuddy-prompts.md) 的 Rn/zn 原文，质量最接近原版。

点名了目标模型时：适配说明放在旁路字段，不写进增强正文。

## 质量标准

下一位助手读完增强结果，不用猜「具体要什么、不要什么、交什么」——同时又没有被扩成另一个项目。变长但在编造技术栈、文件名或回答了原问题，就是失败。

换宿主之后，用同一句草稿应对仍像 [references/examples.md](references/examples.md) 的一段指令。若变成工单、清单或开始办事，是宿主流程坏了，去改适配层，不要改算法和硬约束。
